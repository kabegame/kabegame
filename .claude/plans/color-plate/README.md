## 总体设计思路

每张壁纸在入库时算一份**色盘**（palette）：最多 5 个代表色，每个带面积占比，存进 `images.palette` 一列，同时作为图片的一个列表字段送到前端，在详情的「基本信息」里画成色带。色盘不是原图的精确颜色，而是「缩到 512×512 → 切成 16×16 个区域取平均 → 从这些区域色的包围盒中心向外，把合并半径内的区域收成一个颜色（取成员平均）→ 把平均色仍然相近的再并一遍 → 按占比取前 k 个（累计超过 95% 或 k = 5 即停）」的结果；纯色图只会得到 1 个颜色，不会出现 256 个几乎一样的颜色。视频与 GIF 均匀抽 8 帧，把各帧的区域合在一起聚合；WPE 的网页 / 场景壁纸先取 `project.json` 的 `schemecolor`，没有就用预览图（`preview.gif` / `preview.jpg`）按上面的方法算，再没有就没有色盘。

**距离**是色盘到一个参考色的远近：色盘各颜色到参考色的感知色差按占比加权平均，色差在 OKLab 空间里算、明度差折半，映射成 0–65535 的整数，越小越接近；65536 专门留给「没有色盘」。范围取这么细是为了少并列（0–255 时每个色桶里上千张图同一个距离）。它是 `media::palette` 里的一个纯函数，下面两条排序路都用它，所以同一个颜色不管走哪条路，顺序都一样。

按颜色排序有两条路，对应两个不同的排序段，**用哪一条由前端判断**（颜色在色桶里就用前一条，否则用后一条）：

- **色桶，预计算：`sort/by-color_0x<rrggbb>`**。`color_buckets` 表里是色桶，主键就是 rgb 整数：迁移写入 12 个基本色桶（红橙黄绿青蓝紫粉棕黑白灰），用户可以把自己取的颜色**保存成色桶**，也可以删掉自己存的。**关系表** `image_color_distances(image_id, bucket_rgb, distance)` 存每张壁纸到每个色桶的距离。排序时 INNER JOIN 关系表里该色桶的那一片，按 `(distance, image_id)` 排，正好是索引 `(bucket_rgb, distance, image_id)` 的顺序，翻页沿索引读、不排序。
- **任意颜色，现算：`sort/by-any-color_0x<rrggbb>`**。用户只是点了一个颜色、没有保存时走这条。排序表达式是宿主 SQL 函数 `kb_palette_distance(images.palette, 颜色)`，对全部候选行现算再排序，和随机排序是同一种代价。它不落任何持久状态。

收藏视图存的是路径本身：按现算颜色排序的视图存下来还是 `by-any-color_0x…`，不会替用户生成色桶；以后应用它仍然现算，除非用户另外把这个颜色存成了色桶（那时前端会改用 `by-color_0x…`，顺序相同）。

关系表有一条不变量：**每张图对每个色桶恒有一行**。没有色盘的图（含存量图在回填算到之前）距离是 65536，所以按色桶排序时它们排在最后而不是消失；现算那条路上没有色盘的图同样得到 65536。两条路都不改变结果集与总数——预览定位、轮播起点这些建立在「排序不丢行」之上的机制不用特判。不变量由三处写入维持：迁移同步给存量图铺满 65536；`Storage::add_image` 在同一个事务里写图片行、色盘与它对全部色桶的距离；保存色桶在同一个事务里写色桶行与它对全部图片的距离。删图、删色桶时关系行由显式删除加外键级联清掉。

前端排序下拉多一个「颜色」维度（调色板图标），点它在面板里就地展开色块：12 个基本色桶、用户存的色桶、末尾一个「其它颜色」。点色块按该色桶排序；点「其它颜色」打开内嵌的取色面板，可以「按这个颜色排序」（现算）或「保存为色桶」（存表后按色桶排序）。色桶列表由前端观察 `color_buckets://` 得到，色桶增删发 `color-buckets-change` 事件刷新。`_kb_desc` 照常翻转（最远的在前）。

数据流：

```text
入库（下载 / 本地导入 / 文件夹同步 / WPE）
  → media::palette::compute(来源)            色盘（可能为空）
  → Storage::add_image(image)                image.palette 带着色盘；一个事务：images 行 + palette 列 + 每个色桶一行距离
  → images-added                             行里带色盘；关系行已在，按颜色排序的视图刷新能看到新图

存量图：v052 同步铺 65536 → 回填作业 image_palette 分批算色盘、改写距离、发 palette 补丁

查询（前端按「颜色在不在色桶里」选段）：
  …/sort/by-color_0x<rrggbb>/…      → INNER JOIN image_color_distances ORDER BY distance, image_id      （沿索引）
  …/sort/by-any-color_0x<rrggbb>/…  → ORDER BY kb_palette_distance(images.palette, 'rrggbb'), images.id  （现算 + 排序）
```

关键决策与理由：

1. **色桶预计算存表，没存的颜色现算**。常用的颜色值得用存储换速度：排序走索引，一页与按时间排序同量级，代价是每张图每个色桶一行（12 个色桶时每张图约 260 字节，6.5 万张约 17 MB）。任意颜色有 1600 万种，不该因为用户点过一次就永久占一份全库距离，所以现算；它和随机排序一样要对全部候选行求值再排序，图库很大时一页会慢。用户觉得某个颜色常用，存成色桶就换到快的那条路。
2. **两条路是两个排序段，由前端选**。`by-color_0x…` 只认色桶，`by-any-color_0x…` 认任何颜色；后端不替调用方判断，两个 provider 各自很简单。前端在选颜色的那一刻按色桶列表决定用哪个段，色桶列表变化时再校正一次（色桶被删 → 换成现算段；颜色被存成色桶 → 换成色桶段），两个段对同一个颜色给出相同的顺序。
3. **色桶主键直接用 rgb**，不另设自增 id。路径里的 `0x<rrggbb>`、关系表的 `bucket_rgb`、前端的色块是同一个值，少一层映射。
4. **色盘与距离的计算是 `kabegame_core::media::palette` 里的纯函数**，入库、回填、保存色桶与现算排序都用同一个 `distance_to`（后两者经宿主 SQL 函数 `kb_palette_distance` 调它），不存在两套算法。
5. **色盘是图片的一个列表字段**：`palette` 进 `ImageInfo` 与画廊列表字段（JSON 文本，一行约 60 字节）。不另开按 id 读取的请求：基本信息面板的数据本来就全部来自列表行。随之而来的两点：入库时色盘随 `ImageInfo` 一起交给 `add_image`（签名不变）；回填算出色盘后发 `palette` 字段补丁，已打开的详情与按颜色排序的视图会跟着更新。
6. **聚合是「从包围盒中心向外、按合并半径收点」，不用 k-means**。k-means 要先定 k，纯色图也会被硬拆成 5 个几乎相同的颜色。这里把区域色看成颜色空间里的点，取包围盒中心（固定不变），每次取剩余点里离中心最近的一个当种子，把离它不超过合并半径的点收成一个聚合点、颜色取这些成员的平均，直到取完；再把平均色相距不到半径的聚合点并回去（种子落在色团边缘时一块颜色会被拆开）；个数由画面本身决定，之后再按占比截到 top-k。等价于按到中心的距离排一次序再顺序扫一遍，结果确定、开销可以忽略。合并半径、到中心的距离与到参考色的距离用同一个色差函数。

## 已定事项

色盘：

1. 网格是 **16×16 个区域**（256 个采样，512 的图上每格 32×32 像素）。
2. 聚合：取全部区域色的**包围盒中心**（各通道最小值与最大值的中点），从离它最近的点开始，以该点为种子收走合并半径内的所有点作为一个聚合点，**颜色取成员平均**，再取下一个离中心最近的点；过程中中心不变。取完后**再并一遍**：反复把平均色相距最近且不到合并半径的两个聚合点并成一个。
3. **图片从缩略图算**（≤ 512 的 JPEG；小文件本来就拿原图当缩略图）。**GIF 用原文件抽帧**（缩略图只有第一帧）。**视频从原视频均匀抽 8 帧**（预览只有前 2.5 秒）；原视频解不了时退到预览文件。动画 WebP / APNG 按静态图处理（取第一帧）。
4. WPE 网页 / 场景壁纸取 **`schemecolor` 的作者值**（不跟用户在属性面板里改的值走）；没有就**用预览图算**；连预览图都没有的没有色盘。

距离：

5. 语义是**加权平均色差**（不是覆盖度）。色差函数是 OKLab 欧氏距离、明度差乘 0.5（参照 CMC 2:1 / CIE94 纺织的做法；不折半时白色图会比深绿色图更「接近」纯绿 `00ff00`）。
6. 有色盘的距离取 **0–65535**，**65536 留给没有色盘**，排在最后。

色桶与排序：

7. 两个排序段：`sort/by-color_0xff0000`（色桶，预计算）与 `sort/by-any-color_0x32fe98`（任意颜色，现算）。**用哪个由前端判断。**
8. **基本色桶 12 个**：红 `ff0000`、橙 `ff8000`、黄 `e6c200`、绿 `2e9e3f`、青 `1fb5b5`、蓝 `0000ff`、紫 `8000ff`、粉 `ff80c0`、棕 `804000`、黑 `000000`、白 `ffffff`、灰 `808080`。黄、绿、青不取纯色：纯色和白一样亮，纯白图会排到这三个桶的前 5%–14%，换色后退到 40%–96%，绿桶的前几十张从黄绿变成真正的绿。基本色桶不能删。
9. **用户可以把颜色保存成色桶**（之后按它排序不用现算），也可以删自己存的；最多 24 个，没有名字，显示色块与 `#rrggbb`。保存是一个同步事务：色桶行与全库距离一起提交，6.5 万张约 0.2 秒，100 万张约 5 秒，前端在按钮上转圈，不做忙碌卡片。
10. **只是点一下的颜色走现算**，不进色桶表。**收藏视图保存的是路径**，不会替用户生成色桶。
11. **四个网格都加颜色排序**（画廊、画册、任务、畅游，共用 `GalleryQueryBar`）；虚拟盘不加，MCP 经路径照常可用。

展示：

12. 图片详情的**「基本信息」里显示代表色**：一条按占比分段的色带，悬停显示 `#rrggbb` 与百分比。**点一段 = 当前页面按这个颜色排序**（最接近的在前）：只换排序，过滤与页面上下文原样保留，不跳画廊；导航后关闭预览 / 详情。走的是现算段。
13. **回填期间**没算到的存量图排在最后、基本信息里没有色带；每批算完发 `palette` 补丁，已在手的行就地补上色带，按颜色排序的视图按统一的 500ms 窗口刷新，其它排序的视图只打补丁不刷新。

## 常量与调参结论

合并半径 `0.06`、明度权重 `0.5`、距离满量程 `0.65` 维持原值。P1 结束时用生产缩略图目录（约 3.5 万个文件）做过一轮对比实验，据此定了三件事：聚合后再并一遍、黄绿青三个色桶换色、距离取 0–65535。对比表在 `cocs/gallery/COLOR_PALETTE.md`（P6 写入）。

已知但这一版不处理的现象：淡色粉彩插画容易只剩 1 个颜色；紫桶 `8000ff` 的前几十张偏蓝紫；视频抽帧只落在关键帧上，约一成视频只取到第一帧。基本色桶的 rgb 一旦发版就不宜再改：改它等于换色桶，要迁移重算这些色桶的关系行。
