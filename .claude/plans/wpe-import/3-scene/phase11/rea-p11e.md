# WPE 2.8.42 P11e 按用户属性切换的纹理变体（TEXB0004 条件）静态逆向

**概括**
- **判定器就是绑定管理器 P**（`P = ctx + 0x1708`，虚表 `0x14048df88`），`param_4->vtable[0]` = `FUN_140174a60(P, name, condition)`。读的是 `P+0x10`，即**累计属性全集**（P3 I1 的 `R+0x1728`）：首次加载时是配置里的 `wproperties`（用户当前保存值），运行中是合并过增量的当前值。【确】
  - `condition` 非空：全集里 `name` 必须是 JSON 对象，它的 `value` 必须是 **JSON 字符串**，且与 `condition` 逐字节相等才为真。数字、布尔、null 一律为假（不做 asString 转换）。【确】
  - `condition` 为空（TEXB 条件写成字符串时，字符串本身是属性名）：`value` 必须是 **JSON 布尔 true** 才为真；数字 1、字符串 `"true"` 都为假。【确】
  - 属性不在全集、不是对象 → 假。属性对象存在但**没有 `value` 键**时：布尔分支判假，字符串分支对空指针解引用（汇编 `0x140174d30` 直接读 `[rsi+8]`，没有判空）→ 【推】WPE 崩溃。【确：没有判空；后果【推】】
- **和场景对象 `{user:{name, condition}}`（如 `visible`）不是同一个判定。** 后者在运行时由 `FUN_1401731d0`（`0x14017337b`–`0x1401733fa`）用 jsoncpp `asString(value)`（`FUN_140085cc0`）与条件串比较（`FUN_14000d0f0`），值类型 < 6 都参与，数字会先转成字符串；纹理条件只认字符串类型的值。【确】
- **运行中改属性会重载整张纹理、重新选变体。** 每张有条件的 `.tex` 在加载时给每个出现过的属性名建一个用户绑定（虚表 `0x14048b700`，描述符 setter `FUN_14015ea10`），并在 `P+0x150`（`ctx+0x1858`）登记一个回调（lambda `0x140161a60`）。【确】
  - **setter** 只比较、不重载：新值是字符串取原文、是布尔取 `"1"`/`"0"`，与加载时记下的「命中条件串 / `$__default` / `"1"`/`"0"`」不同就置脏位 `obj+0x148`；数字、null 不置脏。【确】
  - **回调**在 `FUN_1401731d0` 的最后、绑定与脚本 `applyUserProperties` 之后执行：脏了就清位，按纹理名调纹理虚函数 `+8` = `FUN_1400ec220`，**同一个纹理对象原地重新读文件、重新判定条件、重新解码全部 mip、重建 GPU 资源**。【确】
  - **时机**：属性在渲染线程帧间的 0x466 消息里同步应用（P3 I1），重载也在其中完成，下一帧画出新变体。封面消息（`FUN_140171440`）与资源热重载（`FUN_1401830a0`）也走 `FUN_1401731d0`，同样会执行这些回调（只在脏时动作）。【确】
- **纹理缓存键只有文件名**（`FUN_14014cf90`，规整后的名字），不含选择结果。判定读的是全局全集、不分材质，所以同一个 `.tex` 被几个材质用时永远是同一份选择；重载是原地的，所有引用者一起变。【确：键；「一起变」【推】，由「同一对象原地重建」推出】
- **两个副作用**【推，由代码推出】：
  - 没有任何条件命中时记的是 `$__default`，此后**任何字符串新值都与它不同** → 每次应用该属性都重载一次，结果不变。首次加载后 `FUN_140181f30` 会以全集为增量再调一次 `FUN_1401731d0`（P3 I1），所以「无命中」的纹理在加载时就**多重载一次**。
  - 每次重载都会再建一组描述符与绑定并登记到 P（`FUN_140175880` 只按绑定指针去重，新对象指针不同），旧绑定不摘。只是泄漏与重复调用，结果不变。
- **`param_7`**【确】：
  - `& 1`：只读头，不拷贝、不解码 mip 数据，变体也不贴（数据指针为空）；信息查询 `FUN_14014d500`（调用点 `0x14014da66`）用 `1` 且判定器传空，条件根本不判定。
  - `& 2`：每个图像跳过第 0 级 mip（该图像 mip ≥ 2 级时），返回 1，帧表坐标 ×0.5。纹理加载 `FUN_1400ec220` 在全局纹理降级系数 `ctx+0x1218`（`g_TextureReductionScale`）> 1 时传 6，否则传 4。
  - **WPE 缺陷**：跳过第 0 级时**没有读走它后面的变体块**（`0x14015d513` `test r10b, r10b` 直接跳到 `0x14015e118`），第 1 级 mip 的头会从变体块里读出来。【确：读序；后果【推】：降级时带条件的 `.tex` 解析错位、尺寸乱或报 `Invalid texture resolution`】
  - `(& 5) == 4` 且 TEXI 标志无 `0x20`（视频位）且解码器 `vtable[1]`（`0x1400c3520`：线程局部异步上下文存在且开着）为真：FreeImage 编码或 LZ4 的 mip 交给工作线程（解码器 `vtable[2]` = `FUN_1400c3550`），**带着已裁过的变体表**；工作线程 `FUN_1400ce760` 用同一套规则贴变体（位 2 整张替换，否则解码 / 解压后 `FUN_14015c480`）。所以**这条路下变体照样生效**。【确】原始（未压缩）mip 一律同步。
  - 异步开关只在材质刷新 `FUN_140150d60` 里打开（`0x140150daa` 置 1、`0x1401510d2` 置 0）；属性触发的重载在 `FUN_1401731d0` 里，【推】走同步路径。
- **资源编译器**（`resourcecompiler64.exe`）核对了字段来源【确，另注明的除外】：源 JSON 的 `variants` 是数组，**每个元素是一组，组号 = 下标 + 1**；元素的 `options` 每项是一个变体：`file`（必须是字符串）、`variantcondition`（字符串或对象，否则跳过）、`blend`（等于 `"alphablend"` 时标志位 1）。TEXB 里的条件 JSON 就是 `{"condition": variantcondition}`。**变体号是全部组连续编号的计数器，从 1 起**。每级 mip 的变体条目第一个 u32（读入端跳过的那个）是**组号**，x、y、w、h 是该级 mip 上的矩形（右减左、下减上）。标志位 1 只在 `alphablend` 且纹理的某个格式字段为 0 时给出（【推】这个字段就是纹理格式，0 = RGBA8888，与运行时「位 1 且 RGBA8888 才混合」对上）；**位 2 这段代码不产生**，来源【未知】。

## 1. 判定器 `param_4`

### 1.1 来源【确】

- `FUN_14015e580(param_1 = 解码器, param_2 = 判定器, param_3 = 读指针, param_4 = texinfo, param_5 = 帧表, param_6 = 请求, param_7 = 标志)` 把 `param_1`、`param_2` 原样交给 `FUN_14015c8d0` 的 `param_3`、`param_4`（`0x14015e7a7`–`0x14015e7c6`）。TEXV0004 老格式走 `0x14015e900`，判定器传 0。
- 调用点 `0x1400ec47b`（`FUN_1400ec220`，文件纹理加载）：
  ```
  rcx = [ctx+0x158]            // DesktopMediaExtensions，解码器
  rdx = ctx + 0x1708           // P：判定器
  r9  = tex + 0x18             // texinfo
  [rsp+0x30] = ctx+0x1218 > 1 ? 6 : 4
  ```
- 调用点 `0x14014da66`（`FUN_14014d500`，读纹理信息）：`rdx = 0`、标志 `1`。
- `P` 的虚表 `0x14048df88` 槽 0 = `0x140174a60`。`P` 由 `ctx` 构造在 `0x14017d30a` 调 `FUN_140170e70(ctx+0x1708, ctx)` 建，`0x140170e83` 写虚表。

### 1.2 `FUN_140174a60(P, name, condition)`【确】

```
if name == NULL: return 0
prop = P.全集.find(name)                 // FUN_140087490 = jsoncpp Value::find，找不到返回 NULL
if prop == NULL or prop.type != object(7): return 0
v = prop.find("value")
if condition == NULL:
    return v != NULL and v.type == bool(5) and asBool(v)        // FUN_140086300
else:
    // 0x140174d30：不判 v 是否为 NULL
    return v.type == string(4) and asString(v) == condition    // FUN_140085cc0 + FUN_14000d010（strlen + memcmp）
```

- jsoncpp 类型码：0 null、1 int、2 uint、3 real、4 string、5 bool、6 array、7 object。
- 只在 TEXB 里找到它的调用（经虚表，地址没有直接引用）；别处有没有经 `P->vtable[0]` 调它没穷举。【未知】

### 1.3 TEXB 里怎么用（复核已知，补两点）【确】

- 条件 JSON 外层是对象。
  - `condition` 是对象：必须 `name`、`condition` 都是字符串，才调判定器；否则这条条件**什么都不做**，组号、变体表、属性名表都不记。
  - `condition` 是字符串：调 `判定器(P, 字符串, NULL)`。
  - 没有 `condition` 键、JSON 解析失败、判定器为空：同样什么都不做。
- 属性名表 `tex+0x38` 的写法：
  - 对象形式命中 → `表[name] = condition`，**覆盖**；
  - 对象形式没命中 → 表里还没有这个名字时写 `$__default`，已有就不动；
  - 字符串形式 → `表[字符串] = "1"/"0"`，每次覆盖。

  所以同一属性名最终记的是「最后一条命中的条件」，没有命中则是 `$__default`；变体表却是「每组第一条命中的」。

### 1.4 与场景对象条件绑定的区别【确】

- 场景对象的 `{user: {name, condition}}`：
  - 加载时 `FUN_1401a4db0` 只建绑定（`+0x40` 记条件串），不判定。
  - 首次加载后以全集为增量调 `FUN_1401731d0` 时，以及之后每次运行时增量里有该属性名时，`0x14017337b` 起执行：
    ```
    if 绑定.条件串非空 and value.type < 6:
        b = asString(value) == 条件串          // FUN_140085cc0 + FUN_14000d0f0
        setter(&{P, 目标}, 描述符, JSON bool b)
    ```
  - jsoncpp `asString` 会把数字、布尔转成字符串，【推】所以数字值能匹配 `"1"` 一类条件。
- 纹理条件只认字符串值、布尔值，判定在 `FUN_140174a60`，两者不是同一个函数。项目里 combo 的 `value` 写成数字时：场景对象的条件可以命中，纹理变体永远不命中。

## 2. 运行时换图

### 2.1 加载时登记（`FUN_1400ec220`，`0x1400ec7ad` 起）【确】

```
FUN_14015ff20(tex)
if tex.属性名表 非空:                               // tex+0x48
  if tex+0x130 == 0:
    L = new 0x198 { vt 0x14048b7d0, +0x10 = ctx+0x1c88, +0x190 = tex }
    FUN_1401a38f0(L+8, 0)                          // 取对象 id
    P.回调表[L.id] = lambda{L}                     // ctx+0x1858；lambda 虚表 0x14048b7a0，调用体 0x140161a60
  for (名, 串) in tex.属性名表:
    d = new 0x58 { 类型 8, setter FUN_14015ea10, 名字 = 名 }
    L.描述符集合.insert(d)                          // L+0xc8
    L.条件表[名] = 串                               // L+0x108，FUN_140030830
    b = new 0x60 { vt 0x14048b700, +8 = L, +0x10 = d, 名字 = 名, 条件串 = 空 }
    FUN_140175880(P, b)                            // 挂到 P 的「属性名 → 绑定列表」
```

### 2.2 setter `FUN_14015ea10(ctx = &{P, L}, d, value)`【确】

```
L = ctx[1]
e = L.条件表.find(d.名字)                          // 找不到当作 end
if value.type == string: s = value 原文
elif value.type == bool: s = value ? "1" : "0"
else: return                                      // 数字、null 等：什么都不做
if e != end and e.串 != s: L+0x148 = 1            // 只置脏，不更新条件表
```

- 绑定的条件串为空，所以 `FUN_1401731d0` 把增量里的原始 `value` 交给它（`0x140173398` 一支）。

### 2.3 回调与重载【确】

- `FUN_1401731d0(P)` 的最后（`LAB_140174366`，`0x140174366`–`0x14017449f`）：回调表非空时拷一份，逐个调 `std::function`。顺序是：
  1. 增量里每个键的绑定 setter；
  2. 脚本侧 `updateScriptProperties` / `applyUserProperties`；
  3. 回调表。
- lambda `0x140161a60`：
  ```
  if L+0x148:
      L+0x148 = 0
      tex = L+0x190
      if tex+0x10 & 8:                              // 来自文件
          tex->vtable[1](tex, tex+0x78 名字)         // = FUN_1400ec220，尾调用
  ```
- `FUN_1400ec220(tex, 名)` 的重载：
  - 开头释放 `tex+0xd8`、`tex+0x168`、`tex+0x140` 视图列表（【推】GPU 纹理与视图）；
  - 先 `FUN_14017e040(ctx)`（`0x1400ec2ec`）把已完成的异步解码结果交付（按纹理名找回纹理，调纹理虚函数 `+0x18`）；
  - 经文件系统 `ctx+0x1898` 重新读整个 `.tex`（`FUN_1400d4160`，`0x1400ec3be`）；
  - `FUN_14015e580` 开头清空 texinfo 的属性名表（`0x14015e5be`），TEXB 用**当时的全集**重新判定；
  - 解码全部 mip，重建采样器（`FUN_140099980`，`0x1400ed023`）；
  - 最后照 2.1 重新登记。`L` 已存在就复用，条件表按名字覆盖成新命中的串。
- 纹理对象不换，材质里的指针不用动。
- 调用 `FUN_1401731d0` 的三处（`wp.asm`）：
  - `0x140182f5e`：`FUN_140181f30` 的尾调用（属性应用，首次加载与运行时）；
  - `0x140171a8d`：每帧脚本函数里的封面消息；
  - `0x1401833cd`：资源热重载 `FUN_1401830a0`。
- 所以运行中改属性：渲染线程帧间处理 0x466 时就同步重载完，下一帧画新变体（与改 `visible` 同一帧生效）。【推】除非这时异步解码是开的，见 3.3。

### 2.4 缓存与共用【确，另注明的除外】

- 纹理管理器 `FUN_14014cf90(mgr, 名, 不存在就建)`：键是 `FUN_1400187b0` 规整后的名字（FNV-1a 哈希），没找到才调设备虚函数 `+0x60` 建。选择结果不进键。
- 判定读全局全集，与哪个材质引用无关，所以两个材质用同一 `.tex` 时不会出现两种选择。
- 重载原地进行，两处同时换。【推】

### 2.5 由上面推出的行为【推】

- **无命中时反复重载**：条件表记 `$__default`，任何字符串值都与它不同，每次该属性被应用都重载一次，结果不变。首次加载后的全量应用也会触发一次。
- **对象形式的条件配布尔属性**：判定永远为假（要字符串）。setter 拿到 `"1"`/`"0"` 与 `$__default` 比，每次切换都重载，结果都是底图。
- **字符串形式的条件配 combo**：判定要布尔，永远为假，记 `"0"`。setter 拿到 combo 的字符串值与 `"0"` 比，不同就重载，结果仍是底图。
- **CLI `applyProperties`**：增量是 `{键: {value: v}}`（不带 `type`），全集整项覆盖，判定照样能读 `value`，重载照常。
- **绑定重复**：每次重载新增一组绑定，旧的不摘，`FUN_140175880` 只按指针去重。setter 只置脏位，重复调用不改变结果。

## 3. `param_7` 与异步路径

### 3.1 `& 1`【确】

- `local_268 = param_7 & 1`。为 1 时 mip 数据既不解码也不拷贝（`FUN_14015c8d0` 里 `local_268 == 0 && 长度 > 0 && 数据非空` 才处理），mip 条目数据为空，变体块照常读走，但因为底图数据为空，整段贴变体都跳过。
- 唯一用法是 `FUN_14014d500` 读纹理信息，它同时把判定器传空，条件不判定。

### 3.2 `& 2`（跳过第 0 级）与读入缺陷【确：读序；后果【推】】

- `bVar4 = (param_7 & 2) && mip 下标 == 0 && 该图像 mip 数 ≥ 2`。为真时只把返回值记成 1，**直接跳到这一级的末尾**（`0x14015d513`–`0x14015d52c` → `0x14015e118`），不进读变体块的分支（`0x14015d531` 起）。
- 资源编译器对每一级 mip（包括第 0 级）都写变体块（第 4 节），所以条件数 > 0 时，第 1 级的头 `w, h, …` 会从第 0 级变体块的「组数、条数、组号、变体号……」读出来。
- 只在 `g_TextureReductionScale`（`ctx+0x1218`）> 1 时发生，即 WPE 设置里降低了纹理分辨率。

### 3.3 `(& 5) == 4` 的异步路径【确，另注明的除外】

- 条件（`FUN_14015c8d0` 里算 `local_30c`）：`(param_7 & 5) == 4` 且 TEXI 标志无 `0x20`（视频）且 `解码器->vtable[1]()`。
  - `vtable[1]` 在 `0x1400c3520`（Ghidra 没建函数）：线程局部 `[gs:58]+0x2a0` 的异步上下文存在且第一个字节非 0。
- 每一级 mip 走异步的条件：FreeImage 编码（图像格式 ≠ −1）或 LZ4。原始 mip 仍同步。
- 走异步时，把「名字、mip 数据、长度、级号、尺寸、FreeImage 格式、LZ4 标志、解压后长度、**已裁掉位 2 之前条目的变体表**」打包（`local_218` 起），交给 `解码器->vtable[2]` = `FUN_1400c3550` 进线程池。
- 工作线程 `FUN_1400ce760` 解码底图后贴变体，规则与同步路径相同：
  ```
  for v in 变体表:
      if v.标志 & 2: 用 v 的数据整张替换; break
      if w、h 非 0 且 x + w ≤ W 且 y + h ≤ H 且数据非空:
          按底图的方式解码（FreeImage：变体自己的格式；LZ4：解压成 w·h·4）或原样
          FUN_14015c480(格式, v, 像素, 底图, W)
  ```
  与同步路径的两处差别：
  - 边界判断写成 `x + w ≤ W`（u32 相加），同步路径是 `x ≤ W && w ≤ W − x`。只在溢出时不同。
  - 底图解码失败时异步只记日志、继续，同步路径返回 2，整张纹理失败。
- **异步只在材质刷新 `FUN_140150d60` 期间打开**：开头 `0x140150daa` 调 `解码器 +0x38(1)`，末尾 `0x1401510d2` 调 `+0x38(0)`；`+0x38` = `FUN_1400c2c10`，写线程局部上下文的第一个字节。按「8 行内出现 `+0x158]` 的虚调用」扫 `wp.asm` 只找到这两处。
  - 【推】属性触发的重载（`FUN_1401731d0` 里）、首次加载都是同步的。
  - 【未知】有没有别的写法打开它。

## 4. 资源编译器核对（`resourcecompiler64.exe`）

### 4.1 源 JSON（`0x14005ebfe`–`0x14005f037`）【确，另注明的除外】

- 字符串：`variants`（`0x140585d50`）、`options`（`0x140585d60`）、`blend`（`0x140585d68`）、`file`（`0x140585c58`）、`variantcondition`（`0x140585d70`）、`condition`（`0x140581d80`）、`alphablend`（`0x140585d90`）、`.mp4`（`0x140585d84`）。
- 形状（jsoncpp，数组也按 map 迭代）：
  ```
  variants: [                         // 必须是数组
    { options: [                      // 一组
        { file: "…",                  // 必须是字符串，否则跳过这项
          variantcondition: "属性名" | {name, condition},   // 必须是字符串或对象，否则跳过
          blend: "alphablend" }       // 可选
    ] }
  ]
  ```
- `file` 以 `.mp4` 结尾时走另一条路（【未知】：视频变体，没细看），否则解码图片（`FUN_140096c60` / `FUN_140097710`）。
- 每项生成一条记录：`{"condition": variantcondition}` 序列化成字符串（`0x14005ef1e`、`0x14005ef82`），`blend == "alphablend"` 时记一个布尔（`0x14005ef4c`）。

### 4.2 条件表（`0x140062590`–`0x140062711`）【确，另注明的除外】

```
变体号 = 1                                 // 0x14006256c，全局计数
for g in 0 .. 组数-1:
  组号 = g + 1                             // 0x140062593 先自增再用
  for 记录 in 组:
    if 记录没有有效的 mip 图像: continue      // [mip+0x18] == 0
    记录.变体号 = 变体号++
    标志 = 记录.alphablend and 格式字段 == 0 ? 1 : 0   // [rbp+0xb0]
    条件表.push({组号, 变体号, 记录.条件 JSON, 标志})
```

- 写出（`0x14005d060`–`0x14005d0f2`）：`[u32 组号][u32 变体号][u32 标志][JSON][\0]`，与读入端一致。
- 【推】`[rbp+0xb0]` 是纹理格式，0 = RGBA8888，与运行时「位 1 且 RGBA8888 才混合」对上。
- **标志位 2 在这里不产生**。编译器别处是否会给出位 2：【未知】。

### 4.3 每级 mip 的变体块（构造 `0x140062740`–`0x14006296c`，写出 `0x14005d25d`–`0x14005d3f4`）【确】

- 只在条件表非空时写：`[u32 组数]`，每组 `[u32 条数]`，每条：
  `[u32 组号][u32 变体号][x][y][w][h][u32 FreeImage 格式][u32 长度][数据]`。
- 读入端「跳过」的那个 u32 就是组号（1 起）。
- x、y 是该级 mip 上矩形的左、上（`[+0x1c]`、`[+0x20]`）；w、h 是右减左、下减上（`[+0x24] − [+0x1c]`、`[+0x28] − [+0x20]`）。矩形是每级各自算的，【推】是变体与底图不同的区域的外接框。
- 每一级（包括第 0 级）都写，与 3.2 的读入缺陷相关。

### 4.4 对照实例 `tex3817/layer5.tex`【推】

- 两条条件组号都是 1：源 JSON 只有一组，两项。
- 标志都是 0：没写 `alphablend`。
- 条件是 `"1"`、`"3"`：combo 值为 `"2"` 时没有命中，显示底图（底图就是 `"2"` 白丝那一版）；`"1"`、`"3"` 时整组只取第一条命中的那一项贴上。

## 要实测确认的问题

给 WPE 抓帧实验用，工程用 `tex3817`（或复制工程只留 layer5 所在图层）。

1. **运行中切换**：`newproperty` 依次改成 `"3"`、`"2"`、`"1"`（UI 或 CLI `applyProperties`），每次之后抓 1–2 帧。看是否下一帧就换成对应变体；`"2"` 时是否是底图。读码预期：下一帧换好，不需要重载壁纸。
2. **CLI 不带 `type`**：用 `-control applyProperties -properties RAW~({"newproperty":"3"})~END` 改值，是否同样换图（预期会）。
3. **数字值**：生成工程，把 combo 的 `value` 和选项值写成数字 `1` / `3`。纹理变体永远不出现（预期），而同一属性绑的 `visible` 条件照常生效（`asString` 比较）。
4. **布尔属性**：生成工程，两种写法各一张 `.tex`：
   - 条件写成字符串（属性名）：跟随 true / false；
   - 写成 `{name, condition: "true"}`：永远是底图。
5. **同组两条都命中**：两条条件相同，变体内容不同。取 TEXB 里先出现的那一条（预期）。
6. **不同组都命中**：按 TEXB 顺序依次贴；有位 2 的条目时，它之前的全部丢掉。需要能产出位 2 的工具或手改 `.tex`。
7. **alphablend**：带 `blend: "alphablend"` 的 RGBA8888 变体，rgb 按变体 alpha 插值、alpha 取较大；非 RGBA8888 时逐行覆盖。比较像素。
8. **纹理降级**：WPE 设置里调低纹理分辨率（让 `g_TextureReductionScale` > 1）后打开 `tex3817`。是否花屏、缺图或日志出现 `Invalid texture resolution`（读码推测第 1 级 mip 错位）。
9. **重载开销**：无命中（`"2"`）时反复应用同一值，是否每次都有一次文件读取 / 解码（Process Monitor 看文件读、或看帧时间尖峰）。读码预期每次都重载。
10. **共用**：两个材质（两个图层）引用同一个带条件的 `.tex`，改属性后是否同时换。
11. **缺 `value` 的属性**：生成工程，对象形式条件指向一个 `type: "group"`（没有 `value`）的属性，是否崩溃（读码推测空指针）。崩溃组合只照报，不复现。
